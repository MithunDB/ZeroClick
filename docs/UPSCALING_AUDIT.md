# Local upscaling audit (2026-10-20)

This records the distribution gate for ZeroClick's local image upscaler. It is not a license grant. Keep the downloaded engine/model pinned, the notices present, and the release manifest verified.

| Component | Evidence | Packaging consequence |
|---|---|---|
| Upscayl desktop and `upscayl-ncnn` | Their repositories contain AGPL-3.0 licenses; [backend repository](https://github.com/upscayl/upscayl-ncnn), [desktop repository](https://github.com/upscayl/upscayl) | A distributed backend requires AGPL notices and corresponding source. The precise boundary between an independently written SwiftUI front end and the backend must be reviewed before release. |
| Backend build dependencies | The backend's [CMake file](https://github.com/upscayl/upscayl-ncnn/blob/master/src/CMakeLists.txt) links ncnn, libwebp, Vulkan/MoltenVK and OpenMP. [ncnn](https://github.com/Tencent/ncnn/blob/master/LICENSE.txt) is BSD-3-Clause with third-party notices; [libwebp](https://github.com/webmproject/libwebp/blob/main/COPYING) has a BSD-style notice and patent grant; [MoltenVK](https://github.com/KhronosGroup/MoltenVK) is Apache-2.0. | Pin exact revisions, inventory the linked binary with `otool`, and include all required copyright/license/patent notices in the distributed ZIP. Check OpenMP and any Vulkan SDK components actually shipped. |
| Upscayl Lite model | [Model pair](https://github.com/upscayl/upscayl/tree/main/resources/models) (`upscayl-lite-4x.bin`/`.param`) is in the AGPL desktop repository and [model registry](https://github.com/upscayl/upscayl/blob/main/common/models-list.ts). Do not infer weight licensing from the app's AGPL or its UI label. |
| Optional personal models | Upscayl's [custom-model guide](https://github.com/upscayl/upscayl/blob/main/docs/Guide.md) documents `.bin`/`.param` pairs. | Keep optional weights outside the repository and app in `~/Library/Application Support/ZeroClick/Models/`. The release must not include UltraSharp, Remacri, Ultramix, or any user-imported weights. Users remain responsible for their individual model terms. |
| Selected lightweight alternative | The original [Real-ESRGAN repository](https://github.com/xinntao/Real-ESRGAN) has a BSD-3-Clause project license and its [v0.2.5.0 macOS release](https://github.com/xinntao/Real-ESRGAN/releases/tag/v0.2.5.0) includes the `realesr-animevideov3-x4.bin`/`.param` pair (~1.25 MB weights). The [Real-ESRGAN NCNN engine](https://github.com/xinntao/Real-ESRGAN-ncnn-vulkan) is MIT-licensed, and its v0.2.0 macOS binary is arm64/universal. | This is a better-documented redistribution route than the unresolved Upscayl Lite pair. It is optimized for animation/illustration, so label that limitation honestly in the app. Include the BSD and MIT license texts and dependency notices in any release. Do not represent it as Upscayl Lite. |

ZeroClick's `.brisk.toml` bundles everything under `Resources`; `.gitignore` alone cannot stop Brisk from copying ignored weights there. The pinned engine and one selected model are in `Resources/Upscaler`; optional models remain in Application Support. `scripts/prepare-upscaler.sh` can recreate these files from two SHA-256-pinned upstream ZIPs, and `scripts/verify-upscaler-resources.sh` checks the exact nine-file allowlist, hashes, executable bit, and arm64 slice in source and app.

## Personal model test (2026-10-20)

At Upscayl commit `a00d55fee90e0f9435d5eaa86e76700df8199af8`, its model directory contains matching NCNN pairs for `upscayl-lite-4x`, `ultrasharp-4x`, and `ultramix-balanced-4x`. Each pair produced a readable 384×384 PNG from a disposable 96×96 image with ZeroClick's existing local NCNN engine at native 4× scale. This proves the pairs load on this Mac; it does not validate their visual quality across varied photos or change their redistribution terms. Upscayl labels UltraSharp and Ultramix non-commercial in its UI. The exact `.bin` SHA-256 hashes tested were Lite `85ee266b632a765a725425ba6a5620c088c8aa2939a03063b2d83b3462724cc1`, UltraSharp `fb3e279d40d4cddb44db4e684d59e68d0aa39852c8cc14dc3f23ccc7e6eee9c1`, and Ultramix `171cae5968485d366b4fb575d232f98d117d94b766b15f22849cfccde40d2050`.

The user requested these for personal use. Installed copies live only in `~/Library/Application Support/ZeroClick/Models/` in separate UUID folders, where the existing model catalog discovers them. The app bundle, repository Resources, and prepared private release ZIP contain none of these three models. ZeroClick does not download models automatically. A second local run on a 409×512 photo produced readable 1636×2048 outputs from all three pairs with intact layout; visual preference remains subjective. Source: Upscayl's [model registry](https://github.com/upscayl/upscayl/blob/main/common/models-list.ts), [English model labels](https://github.com/upscayl/upscayl/blob/main/renderer/locales/en.json), and [custom model guide](https://github.com/upscayl/upscayl/wiki/Guide).

## Native 8× quality investigation (2026-10-20)

The shipped `realesrgan-ncnn-vulkan` executable and its [upstream usage contract](https://github.com/xinntao/Real-ESRGAN-ncnn-vulkan#full-usages) accept `-s` only at 2×, 3×, or 4×. ZeroClick's 5×–8× path therefore performs additional 4× inference and resizes to the exact requested dimensions; it is not a native 8× model. [Preconverted 8× NCNN pairs](https://github.com/genie-design/ESRGAN-ncnn-models) found in third-party collections are not evidence that this executable supports 8×. A [research 8× model such as UGPNet](https://github.com/hwayoon2/UGPNet) uses a separate PyTorch inference stack and training pipeline, not a drop-in `.param`/`.bin` pair for this app. No candidate with verified photo quality, provenance, license, and compatibility has been approved for installation or distribution.

For a local portrait-quality comparison, `/tmp/zeroclick-finder-qa/personal-lite-qa.png` was processed with single native 4× passes of UltraSharp and Ultramix, producing readable 1636×2048 PNGs at `/tmp/zeroclick-native8-study/`. Visual inspection of both reduced previews shows more faithful facial detail than the earlier twice-inferred Lite 8× portrait; this is a subjective one-image observation, not a general benchmark. A 4× UltraSharp output was also resized to exact 8× dimensions as a non-ML baseline. It does not create new detail, but avoids a second model pass. These experiments did not modify originals, repository Resources, app, or package. Do not assume training a native 8× model will improve faces without controlled comparisons.

## Local runtime spike

Downloaded the two official release ZIPs for a local audit. SHA-256: Real-ESRGAN v0.2.5.0 macOS ZIP `e0ad05580abfeb25f8d8fb55aaf7bedf552c375b5b4d9bd3c8d59764d2cc333a`; NCNN engine v0.2.0 macOS ZIP `f1cc31f13398126ddec25a186b9e50c7ab3e4f2bc011d0222331b43ce2037d3b`. `file` confirms an arm64 slice; `otool -L` lists only Apple system dynamic frameworks/libraries. The engine plus 4× model ran locally on an official disposable 220×220 image and produced a readable 880×880 PNG. A later full-size photo check showed that passing `-s 2` to this 4× model rearranges tiles even though output dimensions look valid. ZeroClick now runs inference at the model's native 4× scale and downsamples locally for 2×/3×. A colored-quadrant test and Finder preview/save check catch this failure. The final package contains only the selected model pair, fixed engine, and notices; Brisk's AppleDouble-containing ZIP is replaced with a clean repack before distribution.
